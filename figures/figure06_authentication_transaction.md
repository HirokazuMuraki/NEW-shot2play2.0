---

# 1. Purpose

Figure06 defines the transaction model used to authenticate
a previously registered device and credential.

The model separates:

- Authentication Request
- One-Time QR Token
- Challenge
- Device Credential
- Signature
- Server Verification
- Authentication Result

The transaction is designed so that possession of the registered
private key is demonstrated without transmitting the private key
to the server.

---

# 2. Authentication Transaction Model

The fundamental processing sequence is:

Authentication Request

        ↓

One-Time QR Token

        ↓

Challenge

        ↓

Device Credential

        ↓

Signature

        ↓

Server Verification

        ↓

Authentication Result

---

# 3. Authentication Request

## Purpose

The relying service initiates an authentication transaction.

## Characteristics

- Creates an authentication transaction context
- Identifies the requesting service context
- Associates the transaction with a server-generated challenge
- Prepares the transaction for one-time authentication

---

# 4. One-Time QR Token

## Purpose

The QR representation provides a temporary transaction reference
that can be captured by the registered device.

## Characteristics

- Randomly generated
- Short-lived
- Single-use
- Bound to the authentication transaction
- Invalid after expiration
- Invalid after successful consumption

The QR token does not itself constitute proof of identity.

---

# 5. Challenge

## Purpose

The challenge provides freshness for the authentication response.

## Characteristics

- Generated by the server
- Associated with the authentication transaction
- Non-reusable
- Verified as part of the authentication response

The challenge prevents a previously generated authentication response
from being reused in another transaction.

---

# 6. Device Credential

## Purpose

The registered device uses its protected credential to produce
cryptographic proof of possession.

## Characteristics

- Private key remains on the registered device
- Private key is not transmitted to the server
- Public verification information is maintained by the server
- Credential use is associated with the registered device

---

# 7. Signature

## Purpose

The device produces a cryptographic response using the registered
private key.

Conceptually:

Challenge

        ↓

Private Key

        ↓

Signature

The signature provides proof that the device possesses the
registered private key.

---

# 8. Server Verification

## Purpose

The server verifies the authentication response.

## Verification Conditions

The server SHALL verify:

- Authentication transaction validity
- QR token validity
- Token expiration
- Token single-use condition
- Challenge association
- Credential association
- Signature validity
- Registration state

Authentication SHALL fail if any required condition is invalid.

---

# 9. Authentication Result

## Successful Result

A successful transaction produces an authenticated state.

The result may subsequently be used as an input to:

- Entitlement evaluation
- Policy evaluation
- Authorization processing

## Failed Result

A failed transaction SHALL NOT establish an authenticated state.

---

# 10. One-Time Processing

The authentication transaction SHALL enforce one-time processing.

After successful authentication:

Authentication Transaction

        ↓

Token Consumed

        ↓

Authentication Completed

A consumed token SHALL NOT be accepted again.

---

# 11. Expiration

The authentication transaction SHALL support short-lived validity.

When the transaction expires:

Authentication Transaction

        ↓

Expired

        ↓

Authentication Rejected

An expired transaction SHALL NOT be revived.

---

# 12. Version 2.0 Extension

Version 2.0 extends the authentication result toward
authorization processing.

Authentication Result

        ↓

Entitlement Context

        ↓

Policy Evaluation

        ↓

Authorization Decision

This separates authentication from the subsequent determination
of what the authenticated subject is permitted to perform.

---

# 13. Security Boundary

The following information remains under device protection:

- Private Key
- Device Credential Secret Material

The following information may be processed by the server:

- Public Verification Information
- Authentication Transaction Identifier
- Challenge
- One-Time QR Token State
- Authentication Result

---

# 14. Replay Resistance

Replay resistance is provided through the combination of:

- One-time QR token
- Short expiration
- Transaction-specific challenge
- Credential-bound verification
- Server-side consumption state

---

# 15. Patent Boundary Candidate

Figure06 represents the transaction relationship among:

- Temporary visual authentication token
- Authentication challenge
- Registered device credential
- Cryptographic proof
- Server-side verification
- One-time transaction completion

The combination of these elements forms a principal protocol
transaction boundary for Version 2.0.

---

# 16. Non-Goals

Figure06 does not define:

- User interface design
- Specific QR encoding format
- Specific cryptographic algorithm parameters
- Detailed transport protocol
- Authorization policy syntax

Those elements are defined elsewhere in the specification.

---

# 17. SVG Design Requirements

The SVG representation SHALL include:

- Client / Device side
- Server side
- One-Time QR Token
- Challenge
- Credential / Signature
- Verification
- Authentication Result
- Version 2.0 authorization extension

The visual flow SHALL clearly distinguish temporary transaction
information from protected credential material.

---

# 18. Design Freeze Decision

Figure06 is designated as the authentication transaction
reference model for NEW-shot2play Protocol Suite Version 2.0.

Future modifications require Design Freeze review.
