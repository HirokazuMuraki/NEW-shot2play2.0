---

# 1. Purpose

Figure07 defines the lifecycle of an authentication transaction
after an authentication request has been initiated.

The model represents the principal authentication states and the
conditions under which a transaction proceeds to successful
authentication or terminates as an invalid transaction.

The state model is intentionally separated from the transaction
message model defined in Figure06.

---

# 2. Authentication State Model

The fundamental state sequence is:

Authentication Requested

        ↓

QR Presented

        ↓

Challenge Issued

        ↓

Response Submitted

        ↓

Verification

        ↓

Authenticated

---

# 3. Authentication Requested

## Purpose

The relying service creates an authentication transaction.

## Characteristics

- Authentication transaction is created
- Transaction identifier is established
- One-time authentication context is initialized
- Transaction is not yet authenticated

The transaction remains unauthenticated until successful verification.

---

# 4. QR Presented

## Purpose

The temporary authentication representation is presented to the
registered device.

## Characteristics

- One-time QR token is available
- Token is associated with the authentication transaction
- Token has a limited validity period
- Token has not yet been consumed

A presented QR token does not itself establish authentication.

---

# 5. Challenge Issued

## Purpose

The server establishes a transaction-specific challenge.

## Characteristics

- Challenge is generated by the server
- Challenge is associated with the authentication transaction
- Challenge is intended for one authentication response
- Challenge provides transaction freshness

---

# 6. Response Submitted

## Purpose

The registered device submits the cryptographic authentication
response.

## Characteristics

- Device uses the registered credential
- Private key remains protected on the device
- Signature is generated over the applicable authentication data
- Response is transmitted to the server for verification

---

# 7. Verification

## Purpose

The server validates the submitted authentication response.

## Required Conditions

The server SHALL evaluate:

- Transaction validity
- Token validity
- Token expiration
- Token consumption state
- Challenge association
- Credential association
- Signature validity
- Registration state

If all required conditions are satisfied, the transaction proceeds
to Authenticated.

If any required condition fails, the transaction proceeds to a
failure state.

---

# 8. Authenticated

## Purpose

Authenticated represents the successful completion of the
authentication transaction.

## Characteristics

- Authentication has been successfully established
- One-time token is consumed
- Authentication transaction is completed
- Authentication result may be passed to subsequent processing

The authenticated state may provide input to:

- Entitlement Context
- Policy Evaluation
- Authorization Decision

---

# 9. Expired

## Purpose

Expired represents termination caused by expiration of the
authentication transaction or its one-time token.

## Transition Conditions

The transaction SHALL transition to Expired when:

- Authentication validity period expires
- One-time QR token expires
- Required response is not received within the validity period

An expired transaction SHALL NOT be accepted for authentication.

---

# 10. Rejected

## Purpose

Rejected represents termination caused by an invalid authentication
attempt.

## Transition Conditions

The transaction SHALL transition to Rejected when:

- Token validation fails
- Challenge validation fails
- Signature verification fails
- Credential association fails
- Registration state is invalid
- Required security condition is not satisfied

A rejected transaction SHALL NOT establish an authenticated state.

---

# 11. Consumed

## Purpose

Consumed represents the state in which the one-time authentication
token has already been successfully used.

## Characteristics

- Token cannot be reused
- Authentication transaction cannot be replayed using the same token
- Subsequent use of the same token SHALL be rejected

Consumed is a terminal control state for the one-time token.

---

# 12. State Transition Rules

## Authentication Requested → QR Presented

The transition occurs when the temporary authentication token is
presented to the registered device.

## QR Presented → Challenge Issued

The transition occurs when the authentication transaction establishes
the challenge required for the device response.

## Challenge Issued → Response Submitted

The transition occurs when the registered device submits the
authentication response.

## Response Submitted → Verification

The server receives the authentication response and begins validation.

## Verification → Authenticated

The transition occurs when all required authentication conditions
are satisfied.

## Verification → Rejected

The transition occurs when one or more required authentication
conditions fail.

## Any Active State → Expired

An active authentication transaction SHALL transition to Expired
when its validity period ends.

## Authenticated → Consumed

Successful authentication consumes the one-time token.

## Consumed → Rejected

Any subsequent attempt to use the consumed token SHALL be rejected.

---

# 13. Replay Protection

Replay protection is represented by the relationship among:

- One-time token
- Token consumption
- Transaction-specific challenge
- Short validity period
- Server-side state

The same authentication transaction SHALL NOT be successfully
processed more than once.

---

# 14. Terminal States

The principal terminal states are:

- Authenticated
- Expired
- Rejected
- Consumed

Once a transaction reaches a terminal state, it SHALL NOT return
to an earlier authentication state.

---

# 15. Version 2.0 Extension

Following successful authentication:

Authenticated

        ↓

Entitlement Context

        ↓

Policy Evaluation

        ↓

Authorization Decision

Authentication therefore establishes identity assurance but does
not by itself establish authorization.

---

# 16. Security Boundary

The state machine SHALL preserve the following security properties:

- Private key remains on the registered device
- Authentication responses are transaction-bound
- One-time tokens cannot be reused
- Expired transactions cannot be revived
- Rejected transactions cannot establish authentication
- Terminal states cannot be reversed

---

# 17. Non-Goals

Figure07 does not define:

- User interface presentation
- QR visual encoding
- Specific cryptographic algorithm parameters
- Transport protocol details
- Authorization policy syntax

Those elements are defined elsewhere in the specification.

---

# 18. SVG Design Requirements

The SVG representation SHALL include:

- Main authentication state sequence
- Verification decision point
- Authenticated state
- Expired state
- Rejected state
- Consumed state
- Version 2.0 authorization extension

The main successful path SHALL be visually dominant.

Failure and terminal-control states SHALL be clearly separated from
the successful authentication path.

No state label or transition arrow SHALL extend outside its
containing visual region.

---

# 19. Design Freeze Decision

Figure07 is designated as the authentication state transition
reference model for NEW-shot2play Protocol Suite Version 2.0.

Future modifications require Design Freeze review.
