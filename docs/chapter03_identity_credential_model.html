Chapter 03 — Identity and Credential Model

This chapter defines the Identity Object and Credential Object models of the NEW-shot2play Protocol Suite Version 2.0.

The chapter establishes the logical distinction between identity, credentials, authentication state, entitlement state, and authorization state.

Normative Status

A conforming implementation MUST preserve the semantic distinction between Identity, Credential, and Authentication objects even when these objects are implemented by the same software component or stored in the same persistence system.

3.1 Purpose and Scope

The Identity and Credential Model establishes the information required to represent a subject and the credentials that may be used to authenticate that subject.

Identity represents the subject.

Credential represents evidence or a mechanism that may be used to establish control of, or association with, that identity.

Authentication represents the result of applying an authentication protocol to the applicable identity and credential information.

These concepts SHALL NOT be treated as interchangeable.

3.2 Identity Model

An Identity Object represents a logical subject participating in the protocol suite.

A subject MAY be:

  • a human user;
  • an organization;
  • a service;
  • a device;
  • an application; or
  • another protocol-defined principal.

An Identity Object SHALL have a stable logical identity identifier within the applicable trust domain.

Representative Identity Object attributes include:

Attribute Description
Identity Identifier Unique logical identifier of the subject.
Identity Type Classification of the subject.
Issuer Authority responsible for establishing the identity.
Creation Time Time at which the identity was established.
Status Current lifecycle or administrative state of the identity.
Trust Domain Domain within which the identity is recognized.

The Identity Object MAY contain additional attributes required by the applicable service or trust domain.

3.3 Identity Identifier

The Identity Identifier uniquely identifies the logical subject within the applicable protocol scope.

An implementation MUST NOT assume that a display name, email address, telephone number, device identifier, or other mutable attribute is itself the canonical Identity Identifier unless the applicable trust domain explicitly defines it as such.

The Identity Identifier SHOULD remain stable across authentication transactions and authorization requests for the same logical subject.

Where an identity is migrated between systems, the implementation SHOULD preserve a traceable relationship between the original and new identity representations.

3.4 Identity Lifecycle

An Identity Object MAY progress through a lifecycle defined by the applicable trust domain.

Representative identity states include: 

Created
   ↓
Active
   ↓
Suspended
   ↓
Reactivated
   ↓
Deactivated

The actual lifecycle MAY contain additional states.

An identity that is suspended or deactivated SHALL NOT be treated as equivalent to an active identity when an applicable policy requires an active subject.

Changes to identity state MAY affect subsequent authentication and authorization processing.

3.5 Credential Model

A Credential Object represents a credential or cryptographic material associated with an Identity Object for the purpose of authentication or trust establishment.

A Credential MAY be:

  • a cryptographic key;
  • a passkey;
  • a hardware-backed credential;
  • a device-bound credential;
  • a certificate;
  • a token; or
  • another credential type defined by the applicable authentication protocol.

A Credential Object SHALL remain logically distinct from the Identity Object to which it is associated.

3.6 Credential Attributes

Representative Credential Object attributes include:

Attribute Description
Credential Identifier Unique identifier of the credential.
Identity Identifier Identity with which the credential is associated.
Credential Type Type and protocol family of the credential.
Public Key or Verification Material Material required to verify credential use where applicable.
Issuer Authority responsible for credential issuance or recognition.
Creation Time Time at which the credential was created or registered.
Expiration Time Time after which the credential is no longer valid, if applicable.
Status Current credential lifecycle state.

Private credential material MUST NOT be exposed through a protocol interface where such exposure would compromise the security properties of the credential.

3.7 Credential Binding to Identity

A Credential Object SHALL contain or be associated with sufficient information to determine the Identity Object to which the credential belongs.

The binding MAY be established through:

  • an explicit Identity Identifier;
  • a trusted credential registry;
  • a cryptographic certificate;
  • a secure registration record; or
  • another trusted association mechanism.

The binding SHALL be verifiable by the authentication process.

A credential that cannot be reliably associated with the claimed identity SHALL NOT be accepted as valid authentication evidence.

3.8 Credential Lifecycle

Credentials SHALL have a lifecycle independent from the logical identity lifecycle.

A representative credential lifecycle is: 

Issued
   ↓
Registered
   ↓
Active
   ↓
Suspended
   ↓
Reactivated
   ↓
Revoked
   ↓
Expired

Not every credential type requires every state.

A credential MAY be revoked while its associated Identity Object remains active.

Conversely, an identity MAY be suspended while one or more credentials remain technically valid.

Authentication processing SHALL consider the applicable state of both the identity and the credential.

3.9 Identity and Credential Separation

Identity and Credential represent different protocol concepts.

The Identity Object answers the question: 

"Who is the subject?"

The Credential Object answers the question: 

"What trusted credential may be used to establish control
of or association with that identity?"

The Authentication Object answers the resulting protocol question: 

"Has the applicable authentication procedure successfully
established the identity for this transaction?"

These three questions SHALL remain logically distinguishable.

3.10 Authentication Object Boundary

The Authentication Object represents the result and state of an authentication transaction.

The Authentication Object MAY contain:

  • Subject Identifier;
  • Authentication Transaction Identifier;
  • Authentication Method;
  • Authentication Result;
  • Authentication Time;
  • Credential Reference; and
  • Authentication Assurance Information.

The Authentication Object SHALL reference the applicable identity but SHALL NOT become the identity itself.

Likewise, an Authentication Object SHALL NOT be treated as an Entitlement Object or Authorization Object.

3.11 Object Relationship

The principal relationship between the objects is: 

Identity Object
      ↑
      │
Credential Object
      │
      ↓
Authentication Transaction
      ↓
Authentication Object
      ↓
Entitlement / Policy / Authorization Processing

The relationship SHALL preserve the distinction between the subject, the credential used by the subject, and the authentication result produced for a specific transaction.

3.12 Identity and Entitlement Separation

An Identity Object represents a subject, whereas an Entitlement Object represents a right, capability, eligibility, or usage qualification associated with that subject.

The existence of an Identity Object SHALL NOT imply the existence of an Entitlement Object.

Likewise, an Entitlement Object SHALL NOT replace the Identity Object when the applicable authorization policy requires identification of the subject.

The relationship MAY be represented as: 

Identity Object
      │
      ├───────────────┐
      │               │
      ↓               ↓
Credential       Entitlement
      │               │
      ↓               │
Authentication        │
      │               │
      └───────┬───────┘
              ↓
       Authorization

This separation permits an entitlement to remain valid or invalid independently of the current authentication transaction, subject to the applicable entitlement and security policies.

3.13 Identity State and Authorization

Authorization processing MAY depend on the current state of the Identity Object.

Examples of identity conditions include:

  • identity is active;
  • identity is suspended;
  • identity is administratively disabled;
  • identity belongs to an applicable trust domain; or
  • identity satisfies a policy-defined classification.

Where a policy requires an active identity, a suspended or deactivated identity SHALL NOT satisfy that condition.

An implementation SHALL evaluate the identity state according to the applicable policy rather than assuming that historical authentication success establishes perpetual identity validity.

3.14 Credential State and Authentication

Credential state SHALL be evaluated when the credential is used for authentication.

A credential that is:

  • revoked;
  • expired;
  • suspended;
  • invalid; or
  • otherwise outside its applicable validity conditions

SHALL NOT be accepted as valid authentication evidence where the applicable authentication policy prohibits its use.

Credential state changes MAY occur independently from Identity state changes.

Accordingly, authentication processing MUST NOT assume that an identity and all credentials associated with that identity always share the same lifecycle state.

3.15 Multiple Credentials

An Identity Object MAY be associated with multiple Credential Objects.

Multiple credentials MAY be used to support:

  • different authentication methods;
  • different devices;
  • different assurance levels;
  • credential rotation;
  • recovery procedures; or
  • different trust domains.

Each Credential Object SHALL remain independently identifiable and independently manageable.

Revocation of one credential SHALL NOT automatically imply revocation of every other credential unless the applicable security policy explicitly defines such behavior.

3.16 Credential Registration

A credential registration operation establishes an association between a Credential Object and an Identity Object.

The registration process SHALL verify the conditions required by the applicable authentication protocol before the credential is accepted.

The registration operation SHOULD establish:

  • Credential Identifier;
  • Identity Identifier;
  • Credential Type;
  • Verification Material;
  • Registration Time;
  • Credential Status; and
  • applicable trust information.

The registration result SHOULD be traceable to the transaction that established the credential.

3.17 Credential Rotation and Replacement

A credential MAY be replaced or rotated without changing the logical Identity Identifier.

Credential replacement MAY be performed because of:

  • credential expiration;
  • credential compromise;
  • device replacement;
  • security policy requirements; or
  • normal credential lifecycle management.

Where a credential is replaced, the implementation SHOULD retain sufficient traceability to determine the relationship between the previous credential and the replacement credential.

The replacement operation SHALL NOT unintentionally create a different logical identity where the applicable identity remains the same.

3.18 Trust Relationship

The Identity and Credential Model depends on a defined trust relationship.

The applicable trust relationship MAY be established by:

  • a protocol authority;
  • an organizational authority;
  • a credential issuer;
  • a registration service;
  • a cryptographic trust anchor; or
  • another explicitly defined trust mechanism.

An implementation MUST identify the authority or trust mechanism used to establish the validity of an Identity Object and the associated Credential Object.

A credential SHALL NOT be accepted solely because it contains an identifier that syntactically resembles a valid identity.

3.19 Security Requirements

The Identity and Credential Model SHALL satisfy the following security requirements.

  1. Identity identifiers MUST be protected against unauthorized modification.
  2. Credential verification material MUST be protected against unauthorized replacement.
  3. Private credential material MUST NOT be exposed through ordinary protocol responses.
  4. Credential revocation state MUST be authoritative within the applicable trust domain.
  5. Identity state changes MUST be propagated to authorization processing where the applicable policy requires such propagation.
  6. Credential state changes MUST be considered by authentication processing.
  7. An identity or credential whose validity cannot be established MUST NOT be treated as valid merely because a previous transaction was successful.

3.20 Relationship to Authentication Protocol

The Authentication Protocol defined in Chapter 04 consumes the Identity and Credential Objects defined by this chapter.

The authentication process SHALL establish whether the presented credential can be accepted as evidence associated with the claimed identity.

The resulting Authentication Object represents the outcome of that process.

The Authentication Object MAY subsequently be consumed by the Entitlement, Policy, and Authorization Layers.

Authentication processing SHALL NOT modify the semantic meaning of the Identity Object or Credential Object merely by producing an Authentication Object.

3.21 Architectural Invariants

The following invariants SHALL apply to the Identity and Credential Model:

  1. An Identity Object represents a logical subject.
  2. A Credential Object represents authentication or trust material associated with an identity.
  3. An Authentication Object represents the result of an authentication transaction.
  4. Identity, Credential, and Authentication Objects SHALL remain logically distinguishable.
  5. Credential lifecycle state MAY differ from identity lifecycle state.
  6. Identity existence SHALL NOT imply entitlement existence.
  7. Authentication success SHALL NOT by itself establish authorization.
  8. Changes to identity or credential validity SHALL be evaluated according to applicable security and authorization requirements.

3.22 Summary

The Identity and Credential Model establishes the foundation on which the Version 2.0 authentication and authorization architecture operates.

The Identity Object represents the subject. The Credential Object represents the credential associated with that subject. The Authentication Object represents the result of applying an authentication protocol to those inputs.

These distinctions allow subsequent protocol layers to evaluate Entitlement, Policy, and Authorization state without conflating identity establishment with permission to perform a requested operation.

The resulting model provides the object-level boundary required for the authentication and authorization separation defined by Version 2.0.
