Chapter 08 — Security Model
Normative Specification

Chapter 08 — Security Model

This chapter defines the security model of the NEW-shot2play Protocol Suite Version 2.0.

The security model establishes the trust assumptions, security boundaries, protected objects, security contexts, threat conditions, and required security properties governing the protocol layers defined by this specification.

The requirements in this chapter apply to the Identity, Credential, Authentication, Entitlement, Policy, Authorization, and Application Layers unless a more specific requirement explicitly states otherwise.

8.1 Purpose and Scope

The purpose of the Security Model is to ensure that authentication, entitlement, policy evaluation, authorization, and service execution remain distinguishable security functions.

The security model SHALL prevent an authenticated identity, Entitlement Object, Policy Evaluation result, or Authorization Decision from being treated as a substitute for another security function unless such substitution is explicitly defined by this specification.

The security model SHALL protect the transition from authenticated identity to authorized Service Execution.

8.2 Security Objectives

A conforming implementation SHALL provide security properties sufficient to achieve the following objectives:

  1. prevent unauthorized access to protected Services;
  2. prevent unauthorized creation or modification of Entitlement state;
  3. prevent unauthorized Policy Evaluation;
  4. prevent unauthorized Authorization Decisions;
  5. prevent unauthorized modification of Authorization state;
  6. prevent unauthorized reuse of expired or revoked authorization state;
  7. preserve authorization semantics across distributed components;
  8. maintain traceability of security-relevant protocol operations;
  9. maintain security state consistency where required; and
  10. fail closed when required authorization conditions cannot be established.

8.3 Security Model Principles

The Security Model SHALL be based on the following principles.

  1. Authentication establishes an authenticated security context but does not by itself establish authorization.
  2. Entitlement establishes rights, qualifications, or other authorization-relevant state but does not by itself constitute Service authorization.
  3. Policy Evaluation determines whether applicable conditions are satisfied.
  4. Authorization produces an explicit Decision governing a protected operation.
  5. Service Execution SHALL occur only within the scope of a valid Authorization Decision.
  6. Security-relevant state changes SHALL be capable of invalidating dependent state.
  7. Security failures SHALL NOT be converted into successful authorization merely because an earlier state was valid.
  8. A downstream component SHALL NOT broaden an upstream authorization constraint.

8.4 Protected Security Objects

The following protocol objects SHALL be treated as security-relevant objects:

Object Security Role
Identity Object Represents the identity subject associated with protocol operations.
Credential Object Represents credential material or credential references used for authentication.
Authentication Object Represents authentication state and authentication results.
Entitlement Object Represents authorization-relevant rights, qualifications, or conditions.
Policy Object Represents rules governing policy evaluation.
Authorization Object Represents authorization state and the resulting Authorization Decision.
Session Object Represents an active protocol or service security context.
Service Object Represents a protected Service and its executable operations.

8.5 Security-Sensitive State

Security-sensitive state SHALL include any state whose modification, removal, replay, substitution, or invalidation could alter the authorization outcome.

Security-sensitive state MAY include:

  • identity binding;
  • credential status;
  • authentication status;
  • Entitlement status;
  • Entitlement validity interval;
  • Entitlement scope;
  • Policy version;
  • Policy Evaluation result;
  • Authorization Decision;
  • Decision state;
  • Authorization Scope;
  • revocation state;
  • invalidation state;
  • security context;
  • transaction state; and
  • Service execution state.

8.6 Trust Model

The Version 2.0 architecture SHALL operate under an explicit Trust Model.

Trust SHALL NOT be inferred solely from network location, transport connectivity, successful authentication, or possession of an Authorization Object.

A component SHALL be trusted only for the security functions and state transitions for which it has been explicitly authorized.

In particular, successful authentication SHALL NOT grant a component authority to create, modify, or broaden Entitlement or Authorization state unless such authority is explicitly assigned.

8.7 Trust Domains

An implementation MAY divide the protocol environment into multiple Trust Domains.

A Trust Domain is an administrative or security boundary within which a defined set of components, objects, and operations share specified trust assumptions.

Trust Domains MAY include:

  • Identity Trust Domain;
  • Credential Trust Domain;
  • Authentication Trust Domain;
  • Entitlement Trust Domain;
  • Policy Trust Domain;
  • Authorization Trust Domain; and
  • Service Trust Domain.

A Trust Domain boundary SHALL NOT automatically imply that all security properties of one Domain are valid within another Domain. Cross-Domain state SHALL be subject to explicit validation and trust rules.

8.8 Trust Establishment

A component that receives security-sensitive protocol state SHALL establish sufficient trust in the source and integrity of that state before relying upon it for a security decision.

Trust establishment MAY include:

  • cryptographic verification;
  • issuer validation;
  • credential validation;
  • object integrity verification;
  • state validation;
  • scope validation;
  • version validation; and
  • revocation or invalidation status validation.

A component SHALL NOT rely upon unverified security-sensitive state to authorize protected Service Execution.

8.9 Security Boundary

The protocol SHALL maintain explicit security boundaries between security functions.

At minimum, the following boundaries SHALL be recognized:

  • authentication boundary;
  • entitlement boundary;
  • policy boundary;
  • authorization boundary;
  • service enforcement boundary; and
  • cross-service trust boundary.

A security boundary defines the point at which security-sensitive state SHALL be validated before being accepted by another security function or Trust Domain.

8.10 Security Boundary Enforcement

A receiving component SHALL validate security-sensitive state when that state crosses a defined security boundary.

Validation SHALL be performed before the receiving component relies upon the state for a security-sensitive operation.

Boundary enforcement SHALL prevent:

  • unauthorized state substitution;
  • scope expansion;
  • trust escalation;
  • unauthorized replay;
  • invalid state propagation; and
  • unauthorized authorization inheritance.

8.11 Security Context

A Security Context is the collection of security-relevant state required by a protocol component to evaluate or enforce a security condition.

A Security Context MAY contain:

  • Identity reference;
  • Authentication state;
  • Entitlement reference;
  • Entitlement state;
  • Policy reference;
  • Policy Evaluation result;
  • Authorization reference;
  • Authorization Decision;
  • Decision state;
  • Service reference;
  • Resource reference;
  • Action reference;
  • transaction state;
  • security state; and
  • validity information.

8.12 Security Context Integrity

A Security Context SHALL preserve the semantic relationship between its constituent security objects.

A component SHALL NOT construct an Allow-capable Security Context from incompatible, expired, revoked, or otherwise invalid security objects.

Where a Security Context is reconstructed in a distributed environment, the reconstruction process SHALL preserve the authorization semantics defined by the originating protocol state.

A failure to reconstruct a valid Security Context SHALL result in Fail-Closed behavior where the Security Context is required for authorization.

8.13 Security Context Propagation

Where authorization processing spans multiple components, the required Security Context SHALL be propagated or reconstructable across the applicable processing boundaries.

Security Context propagation SHALL preserve:

  • identity binding;
  • Entitlement binding;
  • Policy binding;
  • Authorization binding;
  • Service binding;
  • scope restrictions; and
  • security state.

A component SHALL NOT silently discard security state that is required to preserve an existing authorization constraint.

8.14 Security Context Change

A security-relevant change to any object represented within a Security Context SHALL be capable of causing the affected context to become invalid or require revalidation.

Examples include:

  • Identity status change;
  • Credential status change;
  • Entitlement revocation;
  • Entitlement expiration;
  • Policy version change;
  • Policy invalidation;
  • Authorization revocation;
  • security state change; and
  • Service or resource state change.

8.15 Security State Precedence

Where multiple security states apply to the same protected operation, the implementation SHALL apply the most restrictive applicable security state.

An Invalid, Revoked, Expired, or otherwise security-invalid state SHALL take precedence over a previously established Allow state where the invalid state affects a required authorization condition.

A newer security state SHALL NOT be ignored merely because an older state remains cached or otherwise available.

8.16 Security Model Summary

The Security Model establishes the trust and security boundaries required to protect the Version 2.0 protocol architecture.

The model treats Identity, Credential, Authentication, Entitlement, Policy, Authorization, Session, and Service state as distinct security objects and requires explicit validation when security state crosses trust or processing boundaries.

Security Context integrity, propagation, change handling, and state precedence provide the foundation for the threat and security requirements defined in the subsequent sections of this chapter.

8.17 Threat Model

The Version 2.0 Threat Model defines the classes of threats that MUST be considered when implementing, deploying, or operating the NEW-shot2play Protocol Suite.

The Threat Model SHALL consider threats against protocol objects, security state, trust relationships, policy evaluation, authorization decisions, service execution, and the propagation of security context across processing boundaries.

A conforming implementation SHALL NOT assume that successful authentication eliminates threats occurring at subsequent protocol layers.

8.18 Threat Actors

The following threat actors SHALL be considered within the scope of the Version 2.0 security analysis.

Threat Actor Description
Unauthenticated Attacker An entity that has not established a valid Authentication state and attempts to obtain access to protected protocol functions or Service resources.
Authenticated but Unauthorized Actor An authenticated entity that does not possess sufficient Entitlement or Authorization for the requested operation.
Compromised Client A client environment in which application state, local storage, credentials, or security context may have been compromised.
Compromised Service Component A Service-side component that attempts to bypass or modify required authorization enforcement.
Malicious Insider A trusted administrative or operational actor that misuses granted privileges or attempts unauthorized state modification.
Compromised Protocol Component A protocol component that has been compromised and attempts to produce, modify, replay, suppress, or substitute security-sensitive state.
Network Attacker An attacker capable of observing, delaying, replaying, modifying, or injecting protocol messages within an accessible communication path.

8.19 Attack Surface

The attack surface SHALL include every interface through which an attacker may influence security-relevant protocol state or Service execution.

The attack surface includes, at minimum:

  • Identity registration and update interfaces;
  • Credential registration and validation interfaces;
  • Authentication transactions;
  • Entitlement creation and modification interfaces;
  • Policy definition and version management;
  • Policy Evaluation requests;
  • Authorization requests;
  • Authorization Decision propagation;
  • Service enforcement interfaces;
  • revocation and invalidation mechanisms;
  • cross-service protocol interfaces;
  • distributed Security Context propagation;
  • audit and trace interfaces; and
  • administrative control interfaces.

8.20 Threat Classes

Threats within the Version 2.0 architecture SHALL be classified according to the security property or protocol function that may be affected.

Threat Class Primary Target
Identity Threat Identity binding and identity state.
Credential Threat Credential confidentiality, integrity, validity, and lifecycle.
Authentication Threat Authentication state and authentication result integrity.
Entitlement Threat Entitlement creation, scope, validity, and lifecycle.
Policy Threat Policy integrity, versioning, and evaluation semantics.
Authorization Threat Authorization Decision integrity, scope, state, and lifecycle.
Context Threat Security Context construction, propagation, and continuity.
Service Enforcement Threat Application of Authorization Decisions to protected operations.
Propagation Threat Security state consistency across distributed components.
Lifecycle Threat Expiration, revocation, invalidation, and revalidation.

8.21 Identity Threats

Identity-related threats SHALL include attempts to associate a security operation with an incorrect, substituted, duplicated, or otherwise invalid Identity Object.

Examples include:

  • identity substitution;
  • identity impersonation;
  • identity binding corruption;
  • unauthorized identity reassignment; and
  • use of stale identity state.

An implementation SHALL validate the identity binding required by the applicable protocol operation before relying upon downstream security state.

8.22 Credential Threats

Credential-related threats SHALL include unauthorized disclosure, substitution, replay, modification, misuse, or lifecycle manipulation of Credential Objects.

Credential compromise SHALL NOT automatically imply that all downstream Authorization state is valid.

Where credential status is a required authorization condition, a credential status change SHALL be capable of causing dependent security state to require revalidation or become invalid.

8.23 Authentication Threats

Authentication threats SHALL include attempts to obtain or maintain an Authentication state without satisfying the required authentication conditions.

Examples include:

  • authentication replay;
  • challenge substitution;
  • authentication result substitution;
  • stale authentication state;
  • session fixation; and
  • unauthorized reuse of authentication state.

Authentication success SHALL establish only the authentication properties defined by the Authentication Protocol.

An implementation SHALL NOT interpret authentication success as implicit satisfaction of Entitlement, Policy, or Authorization conditions.

8.24 Entitlement Threats

Entitlement-related threats are a primary security concern of Version 2.0 because the Entitlement Object forms the protocol-level connection between authenticated identity and authorization processing.

Threats SHALL include:

  • unauthorized Entitlement creation;
  • Entitlement substitution;
  • Entitlement scope expansion;
  • unauthorized Entitlement modification;
  • Entitlement replay;
  • use of expired Entitlement state;
  • use of revoked Entitlement state;
  • incorrect subject binding;
  • incorrect Service binding; and
  • unauthorized cross-Service reuse.

An implementation SHALL verify the subject, scope, validity, conditions, issuer, and applicable Service binding of an Entitlement before relying upon it for Policy Evaluation or Authorization.

8.25 Policy Threats

Policy threats SHALL include unauthorized modification, substitution, downgrade, replay, or incorrect selection of a Policy Object.

A Policy Evaluation Engine SHALL evaluate the Policy version and policy state applicable to the current authorization request.

A stale Policy version SHALL NOT be used to produce an Authorization Decision when a newer mandatory Policy version applies.

Unauthorized Policy modification SHALL be capable of invalidating dependent Evaluation Results and Authorization Decisions.

8.26 Authorization Threats

Authorization threats SHALL include any attempt to cause a Service to execute an operation that is not permitted by the applicable Authorization Decision.

Examples include:

  • Authorization Decision forgery;
  • Authorization Decision substitution;
  • scope expansion;
  • decision replay;
  • decision reuse after expiration;
  • decision reuse after revocation;
  • decision state corruption;
  • unauthorized decision propagation; and
  • bypass of Service-side enforcement.

An Authorization Decision SHALL be bound to the security context, scope, and conditions under which the decision was produced.

8.27 Security Context Threats

Security Context threats SHALL include unauthorized construction, modification, omission, substitution, or reconstruction of security-relevant context.

A distributed component SHALL NOT reconstruct an Authorization-capable Security Context using incomplete or incompatible security state.

Security Context reconstruction SHALL preserve the dependencies between Identity, Entitlement, Policy, Authorization, and Service state.

8.28 Decision Binding Threats

An Authorization Decision SHALL be protected against separation from the security conditions under which it was produced.

A conforming implementation SHALL prevent an Authorization Decision from being detached from required:

  • Identity binding;
  • Entitlement binding;
  • Policy binding;
  • Service binding;
  • resource binding;
  • action scope; and
  • security state.

A decision that cannot be reliably associated with its required security conditions SHALL NOT authorize protected Service Execution.

8.29 Propagation Threats

Propagation threats SHALL include unauthorized alteration, loss, reordering, duplication, suppression, or inconsistent interpretation of security state as it moves between protocol components.

Where the same Authorization Decision is processed by multiple components, each component SHALL preserve the security constraints associated with that Decision.

A downstream component SHALL NOT interpret a propagated decision as having broader scope than the originating decision.

8.30 Lifecycle Threats

Lifecycle threats SHALL include the unauthorized continued use of security state after expiration, revocation, invalidation, or other security-relevant state changes.

An implementation SHALL define and enforce lifecycle transitions for security-sensitive objects.

At minimum, lifecycle processing SHALL account for:

  • creation;
  • activation;
  • validity;
  • expiration;
  • revocation;
  • invalidation;
  • revalidation;
  • recovery; and
  • final termination.

8.31 Replay Threats

Replay attacks SHALL be considered against all security-sensitive protocol messages and objects for which repeated use could alter a security decision or Service outcome.

Replay protection MAY be provided through transaction identifiers, nonces, timestamps, validity intervals, state tracking, unique object identifiers, cryptographic binding, or equivalent mechanisms.

A replayed security object SHALL NOT be accepted when its lifecycle state or transaction context no longer permits its use.

8.32 Substitution Threats

Substitution threats SHALL include attempts to replace one security-sensitive object, state, or result with another object that is syntactically valid but semantically unauthorized.

Implementations SHALL validate semantic bindings in addition to message syntax and cryptographic integrity.

In particular, successful verification of an object SHALL NOT by itself establish that the object is applicable to the current Identity, Service, Resource, Action, Policy, or transaction.

8.33 Scope Expansion Threats

Scope expansion SHALL be treated as a security violation when an operation obtains permissions, resources, Services, Actions, or conditions broader than those established by the applicable Entitlement or Authorization state.

A downstream component SHALL inherit restrictions from upstream security state.

A downstream component MAY further restrict scope but SHALL NOT broaden a required restriction without a new valid authorization process.

8.34 Revocation and Invalidation Threats

Revocation and invalidation mechanisms SHALL be protected against unauthorized suppression, delay, substitution, or incomplete propagation.

When a security state change invalidates dependent authorization state, the invalidation SHALL propagate to all components that may otherwise rely upon the affected state.

A component SHALL NOT continue to treat a known-invalid Authorization Decision as valid merely because the Decision was previously accepted.

8.35 Fail-Open Threats

A Fail-Open condition occurs when an implementation permits protected Service Execution despite being unable to establish a required security condition.

Fail-Open behavior SHALL be treated as a security threat.

Where a required Authorization condition cannot be established, the implementation SHALL reject the protected operation unless an explicitly defined exception permits continued execution.

8.36 Fail-Closed Requirement

The Version 2.0 authorization architecture SHALL implement Fail-Closed behavior for security conditions that are mandatory for the requested operation.

The following conditions SHALL result in denial or equivalent non-authorized behavior when they cannot be reliably established:

  • required Identity validity;
  • required Authentication validity;
  • required Entitlement validity;
  • required Policy validity;
  • required Authorization validity;
  • required Security Context integrity;
  • required revocation state;
  • required invalidation state; and
  • required Service or resource security state.

8.37 Security Requirements

A conforming implementation SHALL implement the security requirements defined in this chapter together with the normative requirements applicable to the individual protocol layers.

Security requirements SHALL apply to both protocol state and the processing behavior of components that create, evaluate, propagate, or enforce that state.

An implementation SHALL NOT claim conformance solely on the basis of cryptographic message protection if the implementation fails to enforce the semantic security requirements defined by this specification.

8.38 Authentication Security Requirements

The Authentication Layer SHALL establish an authenticated security state only after the applicable authentication conditions have been satisfied.

Authentication state SHALL be bound to the Identity Object for which the authentication was performed.

Authentication state SHALL NOT be transferable to another Identity Object without a new authentication operation.

An implementation SHALL protect authentication transactions against replay, substitution, and unauthorized modification.

Authentication state SHALL have a defined validity condition.

When authentication state becomes invalid and that state is required by a downstream authorization condition, dependent authorization processing SHALL require revalidation or SHALL fail closed.

8.39 Entitlement Security Requirements

The Entitlement Layer SHALL protect the integrity, authenticity, scope, validity, and lifecycle of every Entitlement Object used for authorization.

An Entitlement Object SHALL identify or otherwise securely bind the subject to which the entitlement applies.

An Entitlement Object SHALL define sufficient information to determine its applicable scope and validity.

An implementation SHALL prevent unauthorized modification of:

  • subject binding;
  • Service binding;
  • scope;
  • conditions;
  • validity interval;
  • quantity or usage restrictions; and
  • revocation state.

An Entitlement that has expired, been revoked, or otherwise become invalid SHALL NOT be used as a valid authorization input.

8.40 Policy Security Requirements

Policy Objects SHALL be protected against unauthorized creation, modification, substitution, rollback, and unauthorized version selection.

The Policy Evaluation Engine SHALL evaluate the Policy Object that is applicable to the current request and security context.

Policy evaluation SHALL preserve the distinction between policy conditions and authorization results.

A Policy Evaluation Result SHALL NOT be treated as an Authorization Decision unless the authorization process explicitly establishes that result as an authorization input.

A Policy version that is no longer valid SHALL NOT be used for a security decision when a newer mandatory version applies.

8.41 Authorization Security Requirements

The Authorization Layer SHALL produce an explicit Authorization Decision for each protected operation for which authorization is required.

An Authorization Decision SHALL identify or securely bind the security context under which the decision was produced.

An Authorization Decision SHALL include or reference sufficient information to determine:

  • the authorized subject;
  • the authorized Service;
  • the authorized Resource or operation;
  • the applicable scope;
  • the applicable conditions;
  • the Decision state; and
  • the validity or lifecycle state.

An Allow decision SHALL NOT be considered valid solely because the underlying message is syntactically correct.

8.42 Service Enforcement Security Requirements

A Service that performs a protected operation SHALL enforce the applicable Authorization Decision before executing that operation.

Service enforcement SHALL verify that the Authorization Decision applies to:

  • the requesting subject;
  • the requested Service;
  • the requested Resource;
  • the requested Action;
  • the applicable scope; and
  • the current security state.

A Service SHALL NOT execute a protected operation based solely on Authentication success.

A Service SHALL NOT expand an Authorization Scope beyond the scope established by the applicable Authorization Decision.

8.43 Revocation and Revalidation

Security-sensitive objects and decisions SHALL support revocation and revalidation where their continued validity depends upon changeable security state.

When an Entitlement, Policy, Credential, Authentication state, or other dependency becomes invalid, dependent Authorization state SHALL be revalidated where required by the applicable dependency relationship.

A revalidation operation SHALL evaluate the current applicable security state rather than merely confirm that a previous decision was once valid.

A revoked or invalidated Authorization Decision SHALL NOT be reused for a protected operation.

8.44 Security Event Handling

Security-relevant state changes SHALL generate or otherwise produce events sufficient to permit dependent security state to be updated, invalidated, or revalidated.

Security events MAY include:

  • Identity state changes;
  • Credential state changes;
  • Authentication state changes;
  • Entitlement creation;
  • Entitlement modification;
  • Entitlement expiration;
  • Entitlement revocation;
  • Policy version changes;
  • Policy invalidation;
  • Authorization revocation;
  • Security Context invalidation; and
  • Service security state changes.

A security event that affects an active authorization dependency SHALL be processed according to the dependency and invalidation rules applicable to that state.

8.45 Audit and Traceability

Security-sensitive protocol operations SHALL be traceable to the extent necessary to establish the origin, processing history, and result of a security decision.

Audit records SHOULD permit correlation of:

  • Identity;
  • Authentication transaction;
  • Entitlement;
  • Policy version;
  • Policy Evaluation;
  • Authorization Decision;
  • Service execution;
  • revocation or invalidation event; and
  • resulting security state.

Audit information SHALL NOT be used as a substitute for real-time authorization enforcement.

8.46 Cross-Service Security

Cross-Service use of Entitlement or Authorization state SHALL be subject to explicit Service binding and scope validation.

An Entitlement MAY be reusable across multiple Services only when the Entitlement explicitly permits such reuse and the receiving Service validates the applicable conditions.

A Service SHALL NOT infer cross-Service authorization merely from the existence of a valid authorization state in another Service.

Cross-Service reuse SHALL preserve all applicable restrictions, conditions, validity intervals, and security dependencies.

8.47 Distributed Security

A distributed implementation SHALL preserve security semantics when security processing is divided among multiple components.

Each component SHALL receive or reconstruct sufficient Security Context to perform its assigned security function.

A component SHALL NOT assume that a security condition remains valid solely because another component previously accepted that condition.

Where distributed components maintain cached security state, the implementation SHALL define the conditions under which that state MUST be refreshed, invalidated, or revalidated.

8.48 Security Invariants

The following security invariants SHALL hold throughout protected Service processing.

  1. Authentication SHALL NOT by itself constitute Authorization.
  2. Authorization SHALL NOT exceed the applicable Entitlement scope.
  3. Policy Evaluation SHALL NOT silently broaden security constraints.
  4. A downstream component SHALL NOT broaden an upstream restriction.
  5. An invalid dependency SHALL NOT produce a valid Allow decision.
  6. A revoked Authorization Decision SHALL NOT authorize protected Service Execution.
  7. An expired security object SHALL NOT be treated as unexpired.
  8. A Security Context SHALL NOT contain mutually incompatible security states.
  9. A Service SHALL NOT execute a protected operation when a mandatory authorization condition cannot be established.
  10. Security state changes SHALL be capable of invalidating dependent state where the dependency requires such invalidation.

8.49 Security Failure Handling

Security processing failures SHALL be handled according to the security function affected by the failure.

A failure that prevents reliable establishment of a mandatory security condition SHALL result in a non-authorized outcome.

Security failures SHALL NOT be converted into successful authorization through default values, stale cached state, or implicit assumptions.

Where an implementation cannot distinguish between a valid and an invalid security state, it SHALL treat the affected state as invalid for purposes of protected Service Execution.

8.50 Security Recovery

A security recovery procedure MAY restore operation after a security-relevant failure, provided that recovery does not bypass required authentication, entitlement, policy, or authorization processing.

Recovery SHALL establish a new valid security state or restore a previous state only when the validity of that state can be independently established.

Recovery SHALL NOT reactivate a revoked or invalidated Authorization Decision solely because the decision was valid before the failure.

Where required security state cannot be restored or revalidated, the affected operation SHALL remain non-authorized.

8.51 Security Model Conformance

An implementation conforms to the Version 2.0 Security Model only if it satisfies the mandatory security requirements defined in this chapter and the security requirements of the applicable protocol layers.

A conforming implementation SHALL:

  • maintain the separation between Authentication and Authorization;
  • protect security-sensitive protocol objects;
  • enforce applicable Entitlement and Policy conditions;
  • bind Authorization Decisions to their required Security Context;
  • preserve security constraints during propagation;
  • process revocation and invalidation state;
  • prevent unauthorized scope expansion;
  • enforce Fail-Closed behavior where mandatory security conditions cannot be established; and
  • maintain the security invariants defined by this chapter.

Additional implementation-specific security controls MAY be used provided that they do not weaken or bypass the mandatory security properties defined by this specification.
